# 后端优化路线图

本文档记录「领域服务分层」与「性能/代码质量优化」的思路与落地顺序，便于后续按步骤实施。

---

## 一、方向2：再抽一层「领域服务」做更强聚合

### 1.1 现状

- 当前结构：Controller → 单资源 Service（`alarm_service` / `camera_service` / `area_service` 等）。
- 业务编排、跨资源规则分散在多个 service 或 controller 中。

### 1.2 目标

在「资源型 service」之上，按**业务域/用例**再抽一层**领域服务**，负责「一个用例里要动多个资源、多个步骤」的编排；Controller 只调领域服务的少数几个用例方法。

### 1.3 领域划分与职责

| 域 | 领域服务职责（思路） | 下层可复用 |
|----|----------------------|------------|
| **告警域** | 告警「生命周期」编排：接入事件 → 去重/限流 → 策略匹配 → 推送入队；以及「确认/批量确认」时可能触发的后续动作（如统计、审计）。列表/详情/统计/仪表盘等读请求可继续用现有 `alarm_service`，或收口到「告警域查询」一个入口。 | `alarm_service`、`notification_service`（enqueue）、策略匹配逻辑 |
| **摄像头域** | 摄像头「生命周期」编排：创建/更新/删除时，统一负责「DB + Redis 缓存 + 流注册/注销 + 配置发布」的顺序与回滚语义；启用/禁用时对「推理、直播、心跳」的联动（停推流、清心跳等）。 | `camera_service`、`config_publisher`、`stream_manager`、`core.redis` 摄像头相关 |
| **推送/通知域** | 配置变更的完整闭环：通道/模板/策略的增删改 → 刷新 Redis 快照（或失效）→ 与 worker 的同步；测试发送的入队与参数校验。 | `notification_config_service`、`notification_service`、Redis 快照写入 |

### 1.4 落地顺序建议

1. 先选一个域落地（建议**摄像头域**或**告警域**，选业务变更最频繁的）。
2. 定义领域服务的**接口**（如 `create_camera(...)` / `confirm_alarm(...)` 等）。
3. 将现有 resource service 作为领域内部调用的能力，Controller 只调领域服务。
4. 再逐步推广到其他域。

## 二、方向3：针对某一块做性能与代码质量优化

在**不改变接口契约**的前提下，对「推送、告警、摄像头」中选一块，做性能与代码质量两方面的收敛。

### 2.1 性能优化思路

| 模块 | 现状/问题 | 优化方向 |
|------|-----------|----------|
| **告警** | 列表/仪表盘多条件 count、多段统计。 | 关键统计走**短 TTL Redis 缓存**或定时预聚合；分页列表确保无 N+1（批量查关联、避免循环内查库）。 |
| **摄像头** | 列表里每个摄像头要 `online`、`algorithm_count`、`snapshot_url`。在线状态 per-camera 查 Redis，量大时 round-trip 多。 | 使用 **Redis pipeline** 或按页批量查在线状态；`algorithm_count` 尽量一次查询（子查询/join 或批量 count）。 |
| **推送** | 策略/模板/endpoint 的 Redis 按需读 + 回写。 | 启动时或配置变更后**预热/刷新**热点 key，减少冷启动或首请求延迟。 |

### 2.2 代码质量优化思路

| 项 | 思路 |
|----|------|
| **统一错误处理** | Service 层用少量**业务异常**（如 `NotFound`、`Conflict`、`ValidationError`），Controller **统一映射**为 HTTP 状态码与 body，避免到处 `if reason == "XXX"`。 |
| **事件/配置结构显式化** | 推送、告警相关的事件体与策略配置用 **TypedDict / Pydantic** 定义，避免裸 dict 到处传，便于静态检查与重构。 |
| **可观测** | 关键路径（告警确认、推送入队、摄像头启停）打**结构化日志**（请求/trace 标识、关键 ID），便于排查与后续接 APM。 |

---

## 三、综合建议与实施顺序

1. **先做方向2**：选一个域（建议**摄像头域**或**告警域**）落地领域服务，把「一个用例一条线」的编排收口到领域服务。
2. **再做方向3**：对同一块做「性能 + 错误与结构统一 + 日志」的优化，领域边界清晰后，优化范围也明确。
3. 实施前可针对选定域输出：**领域服务方法列表** + **与现有 service 的边界划分**，再落到具体改法与文件级改动。
